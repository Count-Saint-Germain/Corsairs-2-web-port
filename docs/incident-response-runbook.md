# Runbook: зависание игры (переходы порт → море)

**EN:** Operator runbook for a hung game session (Brave, `http://127.0.0.1:8007`,
repeated port→sea transitions, loading screen stays). Capture diagnostics
first, reset safely second. Contains no cause hypotheses — see
[defensive-lifetime-plan.md](defensive-lifetime-plan.md) for the analysis plan.

---

## Применяется к

Зависание игровой сессии в Brave на локальном origin `http://127.0.0.1:8007`
(сервер `node play.js` / `node scripts/serve_distribution.mjs --port 8007`).
Известный случай: после нескольких переходов «порт → море» остаётся экран
загрузки; журнал тестового запуска сообщил об ошибке доступа к памяти
WebAssembly. Причина в этом документе не обсуждается — только действия
оператора.

Главный принцип: **сначала фиксация диагностики, потом сброс.** Состояние
страницы (консоль, логи runtime) теряется при перезагрузке вкладки; серверная
сторона и файлы на диске сохраняются.

## 1. Сохранение состояния диагностики (до сброса)

Работает, только пока вкладка не закрыта. Выполняйте по порядку:

1. **Консоль вкладки.** DevTools → Console. Экспортируйте или скопируйте
   последние ~200 строк. Обязательно сохраните строки с сообщением об ошибке
   доступа к памяти WebAssembly и любые строки прямо перед ней. В Brave:
   правый клик в консоли → «Save as…» (сохраняет весь лог в файл) — этот файл
   дальше именуйте `console-<дата>-<время>.log`.
2. **Снимок экрана** зависшего состояния (экран загрузки) — обычным средством
   ОС, не из DevTools (чтобы в кадр попало всё окно вместе с адресной строкой
   и origin).
3. **Контекст сценария** запишите текстом: сколько переходов «порт → море»
   предшествовало зависанию, что делалось между ними (бой/карта/меню), было
   ли зависание на входе в море или на возврате в порт — насколько это
   известно оператору без экспериментов.
4. **Журнал тестового запуска.** Если зависание найдено в ходе прогона, у
   которого есть журнал, скопируйте файл журнала целиком рядом с логом консоли
   до того, как журнал будет перезаписан следующим прогоном.
5. **Терминал сервера.** Не останавливайте сервер до окончания захвата;
   при необходимости скопируйте его вывод последнего сеанса.

Не делайте на этом шаге: клики по зависшему экрану, закрытие вкладки,
перезапуск сервера, открытие второго экземпляра игры на том же origin.

## 2. Фиксация версии сборки (доступна всегда, даже если вкладка мертва)

Выполняется на стороне сервера/файлов, из корня репозитория:

```sh
# версия игрового манифеста стриминговой установки
python3 -c "import json;print(json.load(open('distribution/game/manifest.json'))['version'])"
# версия манифеста английского слоя, если он установлен
python3 -c "import json;print(json.load(open('distribution/game-en/manifest.json'))['version'])" 2>/dev/null

# отпечатки исполняемой сборки
shasum -a 256 distribution/build/game.wasm distribution/build/game.js

# идентификация кода
git rev-parse HEAD && git status --short
```

Запишите также: точную версию Brave (меню Brave → «О Brave»), ОС, дату и
время с точностью до минуты, полный origin из адресной строки
(`http://127.0.0.1:8007`). Строка версии манифеста меняется при каждом
изменении состава файлов — именно она отличает сборку, на которой
воспроизведено зависание, от любой другой.

## 3. Безопасный сброс зависшей сессии

Сохранения хранятся браузером отдельно для каждого адреса сайта; у локального
origin `127.0.0.1:8007` собственное хранилище, не связанное с опубликованным
сайтом или другими портами. Перезагрузка вкладки и закрытие вкладки **не
затрагивают** сохранения и установленную игру.

1. После выполнения шагов 1–2 перезагрузите вкладку (F5 / Cmd+R). Если вкладка
   не отвечает на перезагрузку — закройте её и откройте заново
   `http://127.0.0.1:8007/`.
2. Если и это не помогает — перезапустите сервер (`Ctrl+C` в терминале,
   затем `node play.js`) и откройте вкладку заново.
3. После перезапуска: загрузите последнее игровое сохранение (меню игры) или
   воспользуйтесь сохранённым бэкапом через элементы импорта/восстановления
   загрузчика. Прогресс с момента последнего внутриигрового сохранения
   теряется — это известное ограничение, отдельно фиксируйте его в отчёте
   («последнее сохранение было до N-го перехода»).

**Запрещено** (уничтожает установленную игру и все сохранения origin):

- очистка данных сайта для `127.0.0.1:8007` любым способом (настройки Brave →
  «удалить данные сайтов», DevTools → Application → Clear storage, Clear
  browsing data с включёнными данными сайтов для localhost);
- удаление профиля браузера или каталогов пользователя ради «сброса»;
- ручное редактирование содержимого хранилища origin.

Если зависание повторяется сразу при том же переходе после чистого сброса —
прекратите повторять сценарий и передайте собранное из шагов 1–2 разработчикам
(шаблон ниже). Дополнительные попытки воспроизведения в этом документе не
описаны и не требуются.

## 4. Сообщение разработчикам (шаблон)

```text
Сбой: зависание после переходов «порт → море», экран загрузки остался
Среда:
  origin: http://127.0.0.1:8007
  браузер: Brave <версия>, ОС: <ОС>
  дата/время: <UTC или локальное с указанием пояса>
Сборка:
  manifest version: <из шага 2>
  game-en manifest version: <или «не установлен»>
  game.wasm SHA-256: <из шага 2>
  git commit: <из шага 2, + «dirty» при незакоммиченных изменениях>
Сценарий: <текст из шага 1.3, без домыслов>
Захвачено:
  console-<дата>.log — прилагается; строки ошибки доступа к памяти: <номера строк>
  журнал тестового запуска: <прилагается / нет>
  скриншот: <прилагается / нет>
Не захвачено: <что именно и почему>
```

Отчёт и вложения храните локально рядом с журналом; публиковать их (в issue,
чат, в git) можно только по решению владельца репозитория — вложения могут
содержать производные игровые данные.
