# Publication readiness

The standard build is in `distribution/`. It passed a full integrity check of 9 826 game files and the English layer, including SHA-256, and contains 13 videos. A clean browser installation, the start of the game, saving and reloading were previously checked for this candidate; restoration of a save archive was checked separately. Local HTTP checks and packaging regression tests passed. Touch controls were checked in a browser's phone emulation. The unresolved click latency report and the experimental nature of streaming described below prevent a claim of complete publication readiness.

Before publication, choose a host and verify its COOP/COEP/CORP isolation headers, file types, Range requests, and a short run with saving. A real iPhone and Safari have not yet been tested; emulation does not establish their behaviour. Extended play and listening to audio were not performed at the owner's request.

The cause of the previously observed `guest heap exhausted` error has not been established: the code now collects limited information if it recurs, but this does not prove that its cause is fixed. Earlier tests establish a deployment candidate with known limitations; they do not establish that every device and gameplay scenario is free of errors.

For development after cloning, see the [build instructions](BUILD_FROM_CLONE.md). Publication and connecting a remote Git repository have not been performed.

During Git preparation, the index was exported to a separate clean directory. All 9 826 game files and 771 English-layer files were restored from it; their hashes and the correspondence of the ready build to the source files were verified. The local HTTP server and restoration tests were checked. A full recompilation in a new environment was not performed; setup instructions for the required toolchain are included in the repository.

An additional launch check used a separate clean, normal Chrome for Testing profile: all 2 351 MB of game data was installed, the main menu opened, and “New Game” loaded the character into the cabin. No unhandled page errors were observed. In a Vivaldi private window, installation stopped at 1 314 MB because of the storage quota; support for that mode is not confirmed. The temporary profile and test data were removed.

The project's Python scripts have since been migrated to Node.js, including the local server, packaging and verification, asset preparation, audits, the x86 translator and their test tools. The external Emscripten SDK still requires Python for rebuilding; running the ready distribution requires Node.js. The new translator reproduced the previous output byte-for-byte for all 46 game executables and modules. The Node distribution verifier checked the full hashes again (9,826 base files and the English layer), and the Node server was used for a fresh browser installation that reached the game menu. On 16 November 2026, the project was tested on Node.js 18.20.8 on macOS ARM64. Both the bundled game and a cleanly rebuilt WebAssembly version reached the opening cabin in a browser; the rebuild and distribution packaging passed, including full SHA-256 verification. The Emscripten SDK used its own Node.js 24 internally. The optional Chromium automation used locally installed Playwright 1.65 under Node.js 26 because that Playwright version requires Node.js 20 or later. See [development instructions](BUILD_FROM_CLONE.md) and [recompiler testing notes](../korsary2-next/recomp/translator/README.md) for dependencies and the differential tester's timeout limitation.

The Node.js 18 verification also fixed the test environment's WebCrypto setup, made the Cloudflare Worker explicitly an ES module, and corrected Brotli stream cancellation, lifetime and backpressure. Regression tests cover a live decoder across garbage collection, cancellation and abort with blocked writes, and a slow consumer; Chromium/OPFS installation and corruption checks passed after the changes. These checks do not replace testing on a real iPhone or a deployed host.

A GitHub preparation check found no tracked files above 50 MiB; a locally generated initial push pack was approximately 1.15 GiB. A separate clone restored the original game and English layer, started the ready build in a browser, and rebuilt the browser and headless WebAssembly binaries byte-for-byte using an installed Emscripten SDK. Git attributes now preserve all tracked original game data under `core.autocrlf=true`; the check covers the complete tracked game tree. No GitHub remote was configured, so an actual push was not performed.

A Brave installation was initially blocked by its privacy-capped 2 GiB storage estimate, despite sufficient actual space. The launcher now treats that specific Brave estimate as unknown and still stops on real quota errors. A full installation in Brave subsequently reached the game menu. During server installation, failed writes preserve previously installed game files; regression checks cover new and existing files, quota failures, partial downloads and hash mismatches. Save replacement keeps restore points, and a failure to update or remove an associated language/time record is reported. The launcher and browser tab now display `Corsairs 2`, while the existing storage identifier remains unchanged for save compatibility.

## Follow-up: Brave input and progressive loading, 16 November 2026

In the installed Brave browser, `navigator.keyboard` existed but its `lock` method was unavailable, so no Keyboard Lock permission prompt appeared. A short press of Esc in native fullscreen therefore remains controlled by the browser. In a separate game tab, the new **F10** fallback and the on-screen **Esc** button both returned from Options to the main menu while keeping fullscreen. On Macs with media keys, the user may need **Fn+F10**. The fallback does not change Brave's privacy settings. This run did not establish that Pointer Lock had actually been granted; its fallback state, overlapping keys, releases, focus loss and netplay mapping have automated coverage. The missing method is consistent with an [open Brave issue](https://github.com/brave/brave-browser/issues/50719), but this test alone does not establish which individual setting caused it.

The installed Brave browser does not expose Keyboard Lock in the tested configuration. A double-Esc shortcut is implemented for browsers that grant Keyboard Lock: the first press reaches the game and a second distinct press within 600 ms exits fullscreen. It cannot override the browser when Keyboard Lock is unavailable; use F10 or the on-screen Esc button there. Automated tests cover granted and denied lock, key repeat, key release, timeout and loss of focus. A separate headless Chromium 158 test verified the real Keyboard Lock and fullscreen APIs with automated key presses; a physical keyboard and permission prompt were not tested.

The original game configures a 150 ms delay for some save/load and confirmation buttons; ordinary main menu entries do not have that explicit delay. In an instrumented, separate in-app Chromium test, opening a save list caused one GPU queue pump to block the browser thread for approximately 12 seconds. The updated pump yields during a long queue, retaining command order and readback boundaries; a deterministic regression test covers those properties. With the updated WebAssembly, the same experimental save list opened in approximately one second of automation wall time and the saved cabin loaded successfully. An isolated test of the updated ordinary build also opened its save list and loaded its existing test save. Individual GPU draw and present commands still reached approximately 65 ms during the instrumented test. This identifies and fixes one reproducible long blockage, but does not establish that every reported Brave click delay has the same cause; the updated ordinary build still needs confirmation in Brave.

Progressive resource loading is a **separate experiment**, not the default installation. It requires a specially built WebAssembly binary and runs in its own OPFS game root, userdata root, version identity and partial-install marker; it does not use the standard game root or its saves. The experiment currently supports Russian solo play only. It downloads a minimal starting set, then fetches individual resources on demand from the manifest. In a clean in-app browser test on macOS using a separate localhost origin, it reached the opening cabin and Malcolm's dialogue; 148 additional resource requests completed with no reported failures. Those 148 files totalled 33,102,377 unpacked bytes and 15,289,562 compressed-record bytes according to the client. After reloading that origin, it reached the main menu without repeating the bootstrap or fetching those cached menu resources. This was a short initial-scene test and does not establish later gameplay, all file-access paths, real-iPhone behaviour, or deployment-host compatibility.

The initial selected records total 13,294,690 unpacked bytes and 4,076,639 compressed-record bytes in the current manifest. These are **not** total network transfer figures: the manifest, JavaScript, WebAssembly, Range-request gaps, retries and subsequently requested resources add traffic. The ordinary installation remains approximately 1.27 GB of initial transfer and 2.35 GB unpacked. Partial loading may eventually accumulate more data as the player visits more content.

The prototype serializes cooperating updates and game starts using Web Locks, checks cached immutable resources against their sizes and hashes before starting, and fails closed on a partial or damaged cached file. Automated checks cover protected SAVE paths, a leftover zero-length placeholder, concurrent reads, identity changes and simulated network/integrity errors. After the concurrency fix, a freshly built experiment again reached the opening cabin and dialogue on a clean origin; a reload passed cache verification and reached the menu without fetching cached resources. Following an interrupted or failed download, automatic recovery of a damaged placeholder is not yet implemented; the experiment may require manual investigation. Do not treat the prototype as a replacement for the standard build, and do not delete the standard saves to test it.
